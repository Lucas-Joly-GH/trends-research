# FX Journal

Findings, negative results and decisions behind the FX section of
`trading_book.py`. The code's comments carry the *why* of what stands; this
carries what was tried, measured and rejected, so it is not retried.

The rates are written here as `FX/<CCY>.csv`, one file per rate, by
`trading_book.py`. There is no separate FX script and there should not be one —
see "Why this lives in trading_book.py" below.

---

## 2026-08-28 — Three sources, one in use

Each file holds three rates per session:

```
date, Derived_Rate, NDU_Rate, YF_Rate, NDU_diff_bp, YF_diff_bp, Status
```

**The book reads `Derived_Rate` and nothing else.** `NDU_Rate` and `YF_Rate`
exist to disagree with it.

The reasoning is about failure mode, not accuracy. A conversion rate is the one
input in this pipeline that is both silently wrong-able and catastrophic when
wrong. A rate off by 100x does not raise — it sizes a position 100x wrong and
every downstream number stays plausible. Two independent sources beside the one
in use convert that from an invisible failure into a printed one.

---

## 2026-08-28 — Why this lives in `trading_book.py`

It was first built as a standalone `FX/fx_master.py` reading the contract CSVs
directly. That was wrong twice over, and both reasons are worth keeping:

1. **The derivation needs a worksheet, and trading_book already has one.** Option
   B needs every listed month and its maturity per session — which is exactly
   what `front_contract.py` produces and `cached_worksheet()` caches.
   `till_last_trade_cd` *is* the T in the parity formula, in calendar days. A
   separate script re-read and re-cached the whole panel to reconstruct
   something this one already held, and applied its own gate-date logic to do
   it.
2. **The emit grid is only knowable from inside a book run.** The files are
   written on the book's own session union — the same `grid` XS_trend is scored
   on — so every FX file lines up row-for-row with every book. Nothing outside
   the run knows that grid.

Everything is generated by `trading_book.py`.

## 2026-08-28 — Where the spot rate comes from: no spot exists

**NDU has no spot FX.** The Forex Spot database contains exactly one symbol,
`$USDX`, which is the dollar index, not a rate. So the rate has to be derived.

| | approach | verdict |
|---|---|---|
| A | front contract price as-is | carries the full basis |
| B | implied spot, extrapolated to T=0 from the two nearest contracts | **adopted** |
| C | vendor's unadjusted continuous (`&6E`) | measured, kept as the check |

### B vs C, measured against yfinance on ~29,000 joined observations

```
source            signed mean        mean abs      median      p95      max
Derived (B)     -0.009% .. -0.029%     0.316%      0.202%    0.977%   17.459%
NDU (C)         -0.168% .. +0.315%     0.397%      0.284%    1.132%   17.488%
```

B won all five currencies. But **the deciding number is the signed mean, not the
average error** — the two differ by only 0.08pp on absolute error, which alone
would not justify the extra machinery.

B's signed bias is within ±0.03% of zero in every currency. C's is not: JPY
+0.315%, AUD −0.168%, EUR +0.106%. That is the basis showing through, and it has
a sign. A persistent offset does not average out over a backtest; scatter of the
same size does. JPY is worst because it has the widest rate differential, which
is exactly where a front-contract price sits furthest from spot.

C was **not discarded** — it became `NDU_Rate`. Being a near-copy of a different
construction is precisely what makes it a useful check.

### `&6E_CCB` is disqualified outright

```
&6E       1999 close 1.1866   2026 close 1.16565   range 0.8296 - 1.5964   <- real
&6E_CCB   1999 close 1.4543   2026 close 1.16565   range 1.0433 - 1.8069   <- shifted
```

EURUSD was ~1.18 in January 1999 and never 1.4543. Panama preserves differences,
not levels, and a conversion rate is purely a level. Recorded because `_CCB` is
the symbol used elsewhere in this repo for trend work, so reaching for it is the
natural mistake.

## 2026-08-28 — Negative result: filtering for live quotes changes nothing

Deferred FX months are frequently settlement-only — zero volume, zero open
interest, an unchanged price for weeks. `6E-2026U` opens in 2021 with
`1.2587,1.2587,1.2587,1.2587,0.0,0.0`. The concern was that a stale quote could
set the extrapolation slope.

Requiring `volume > 0 or open_interest > 0` on the two nearest contracts left the
last session **identical to six decimal places in all five currencies**. The
nearest two *are* the liquid two, so the filter never binds. Not applied: a
branch and a fallback path for no gain.

## 2026-08-28 — The alert rows adjudicate in favour of the column in use

Thresholds come from the measured distribution, not from roundness: WATCH at
100bp ≈ the 95th percentile, ALERT at 300bp well outside normal operation.

**26 ALERT rows across the whole book.** 25 have all three sources, so the
outlier is identifiable as whichever source the other two agree against:

```
yfinance is the outlier   25
NDU is the outlier         0
DERIVED is the outlier     0

median |derived - NDU|        8.8 bp
median |NDU - yfinance|     444.2 bp
```

**Zero rows where the column in use is the outlier.** Two external causes:

- **yfinance repeats stale closes.** In EUR 2008 alone, 253 rows carry only 240
  distinct closes; one value appears on three dates. `1.5570987462997437` is
  returned for both 2008-01-08 and 2008-02-08, identical to 16 significant
  figures. The alert dates cluster on the 8th of the month for this reason.
- **Event days with huge intraday ranges** — 2016-06-24 (Brexit), 2020-03-13/18
  (COVID), 2022-09-23 (gilt crisis), 2025-04-04/09 — where a futures settlement
  and a yfinance daily close are struck at different times. `NDU_diff_bp` is
  single digits on all of them.

### The rows yfinance cannot arbitrate

JPY 1979–81, where only NDU is available to compare:

```
date          derived JPY/USD    NDU JPY/USD
1979-09-18          225.4           218.0
1979-10-01          227.2           220.2
1979-10-22          236.4           227.5
```

USDJPY actually traded around 224 in September 1979 and 220 in October.
**Derived is the closer of the two**, so the pattern holds even where the
independent check runs out. (These now fall outside the emitted range for JPY,
which starts 1979-12-04 on the book grid; they were measured on the raw panel.)

## 2026-08-28 — JPY carries a ÷100 that nothing in the metadata records

6J quotes **USD per 100 JPY**. Last close 0.6287 → rate 0.006287 → 159.1 JPY/USD.

`instrument_mapping.csv` cannot help: 6J's pointsize is identical to EUR's and
CHF's. Nothing in the panel, the metadata or the vendor's fields flags it. It is
hard-coded in `FX_CCY` with a note.

This is the exact failure the check columns were built for, and they catch it: an
unscaled JPY shows a **9,900% disagreement against both** other sources rather
than a plausible-looking rate.

## 2026-08-28 — HKD is held at the peg

HKD has no instrument anywhere — not in the panel, not in NDU. Held at 7.80, so
1/7.80 = 0.128205. The HKMA has defended a 7.75–7.85 band since 2005.

Measured against `USDHKD=X`: **+0.178% signed, 0.378% mean absolute, 2.053%
worst** — the same order as the derivation error on currencies that *do* have a
future, which is what makes the peg good enough. Three rows in the whole history
reach WATCH; none reach ALERT.

HSI is the only HKD instrument in the book.

## 2026-08-28 — `USD.csv` is supposed to look like that. It is not broken.

Open it and every column but two is empty:

```
date        Derived_Rate  NDU_Rate  YF_Rate  NDU_diff_bp  YF_diff_bp  Status
1978-03-07  1.0                                                       UNCHECKED
1978-03-08  1.0                                                       UNCHECKED
1978-03-09  1.0                                                       UNCHECKED
```

12,552 rows, `Derived_Rate` is `1.0` on every one of them — one distinct value in
the whole file — `Status` is `UNCHECKED` throughout, and all four other columns
are 100% null.

**This is correct, and it is correct because the portfolio is denominated in
USD.** The rate converts a local-currency amount into the account's currency.
For a USD instrument those are the same currency, so the conversion is the
identity and 1.0 is the only value it can take. There is nothing to derive,
nothing to check it against, and no source that could disagree — hence no
`NDU_Rate`, no `YF_Rate`, no diffs, and a `Status` that says the row was never
checked rather than pretending it passed a comparison that did not happen.

**Why the file exists at all**, given that it holds one number: 45 of the 63
instruments are USD, and generic caller code — "look up the rate for this
instrument's currency" — would otherwise have to special-case the most common
currency in the book. A missing file and a rate of 1.0 are different things, and
only one of them is right. Writing it out means every currency is reached the
same way.

It also spans the **full book grid, 1978-03-07 to 2026-08-27**, wider than any
other file here, while EUR starts 1999 and AUD 1987. That is deliberate too: the
identity is defined on every date that has ever existed, so unlike a derived rate
it has no inception to respect, and ZC's book reaches back further than any FX
contract ever traded.

**If this ever changes**, it will be because the account is no longer in USD, and
the fix is not in this file — it is in `FX_CCY` in `trading_book.py`, where the
`fixed=1.0` entry marks which currency is the base. Every other rate would then
need re-expressing against the new base.

## 2026-08-28 — Two alignment traps, both closed in the output

Neither is hypothetical; both were hit during the build.

**A plain join on date used to leave 98–224 nulls per instrument.** Markets keep
different holidays, so a book date is often absent from a currency's native
sessions. Fixed by emitting on the book's session union and carrying rates over
gaps with a backward as-of, which is what a desk does with a rate over a holiday.
A plain `join(on="date")` is now correct for every instrument.

The one exception is real and must stay: **YAP4 gets 983 nulls against AUD**,
because YAP4's book starts 1983-02-16 and the AUD future starts 1987-01-13.
There is no AUD rate before 1987 and inventing one would be worse than a null.

**`pl.read_csv` returned `Derived_Rate` as a String.** The book grid reaches ~433
sessions before the first FX contract ever traded, so the files opened with a run
of blanks longer than polars' dtype-inference window. Fixed by trimming each file
to start where its rate starts — those rows carried no information. Interior
nulls cannot occur, since the as-of carry fills every session after the first.

`NDU_Rate` and `YF_Rate` can still trip inference, because yfinance starts in
2003 while the files start in 1979. Note the trap is *data-dependent*: it would
quietly fix itself if the panel started later and return the first time an
earlier contract is added, so getting away with a bare `read_csv` once proves
nothing.

**Settled by the dual-write.** Each rate is now also written as
`FX/<CCY>.parquet`, holding an identical frame (verified for all seven), where
dtypes travel in the file and no inference happens. `trading_book.load_fx(ccy)`
reads the parquet when it is current and falls back to the csv with the schema
named, so both paths are correct. See `Trading_Book_Journal.md`, 2026-08-28, for
the measurement and for why trimming history was rejected.

## 2026-08-28 — What `Update.py` now checks, and why these checks

`verify_fx` is a separate report from `verify_books` because **the rates fail
differently**. A book that goes wrong usually goes visibly wrong — a column
empties, a schema drifts, a date stops advancing. A conversion rate that goes
wrong stays perfectly well-formed and simply carries the wrong number; every
position sized off it is then wrong by that factor, with nothing reading as an
error anywhere. So these checks are weighted toward **value plausibility** where
the book's are weighted toward structure.

Sixteen checks, of which the load-bearing ones are:

| check | what it actually catches |
|---|---|
| no session move > 15% | a dropped scale factor (9,900%) or an inversion (~100%) |
| USD is exactly 1.0 | the base currency silently redefined |
| HKD sits exactly on the peg | the peg constant edited or drifted |
| `Derived_Rate` fully populated | a hole left mid-history by the as-of carry |
| csv and parquet agree | the dual-write halves diverging |
| parquet twin present and current | a run that died between the two writes |
| ALERT share under 1% | a check source quietly going bad |

Plus, on the book side: `FX_rate` present in all 63, **matching the
instrument's own currency's file**, and no book entirely null.

### The 15% ceiling is set from the panel, not from intuition

The largest genuine day-over-day moves in 47 years of these rates:

```
AUD  9.47%  2008-10-06   the GFC
JPY  8.65%  1998-10-07   the carry unwind
GBP  7.81%  2016-06-24   the Brexit referendum
CAD  5.29%  2008-10-29
EUR  3.35%  2015-12-03
```

15% clears every one of them while staying an order of magnitude below the
failures it is aimed at. **This is the check that would have caught the JPY ÷100
problem** had it ever shipped.

### Every check was fault-injected, not just observed passing

A check that has only ever passed is not yet a check. Seven faults were injected
into copies of the real outputs and every one was caught by its intended check:

```
injected fault                    check that fired
USD no longer 1.0                 USD is exactly 1.0 (base currency)
JPY scale factor dropped          no session move > 15%
EUR parquet missing               parquet twin present and current
EUR parquet stale                 parquet twin present and current
EUR csv/parquet disagree          csv and parquet agree on Derived_Rate
CGB priced with the EUR rate      FX_rate matches the instrument's own currency
ZT parquet stale                  parquet twin present and current
```

The wrong-currency case is the one that most needed proving: a CGB priced with
the EUR rate is off by 61% and every downstream number still reads as a
plausible dollar figure. The only way to catch it is to re-derive the currency
from the mapping and compare against that currency's own file, which is what the
check does.

`FX_CCY` and `HKD_PEG` are **imported from `trading_book.py`, not restated** in
`Update.py` — a currency added there and forgotten here would make the check
pass while the stage it guards aborts, which is worse than no check.

## Conventions

- **Every rate is CCY → USD.** Multiply a local amount by it to get USD. Fixed
  everywhere including the checks, so an inversion error shows up as a ~100%
  disagreement rather than a plausible number.
- **The diffs are computed on exact date matches, before the as-of carry.**
  Comparing a stale carried value against a fresh one would manufacture
  disagreements out of holidays and put them in the column meant to reveal real
  ones.
- **A null `Derived_Rate` stays null.** Never backfilled from the checks even
  when both are present — a column named `Derived_Rate` that is sometimes not
  derived is a worse object than a null. `Status` says `NO_DERIVED`.
- **The two check columns are independently optional.** NDU down or the network
  unreachable leaves that column null and the build succeeds; a build that raises
  is not cached, so a transient failure does not become a sticky empty. An FX
  failure never discards the books — they are already written.
- **The checks are keyed on the panel edge**, which stands in for "a new session
  exists", since there is no local file to fingerprint. They refetch exactly when
  new data arrives and a same-day rerun is free.
- **`--no-fx` skips the rates entirely; `--no-fx-checks` builds them from the
  local panel with no vendor and no network.**
